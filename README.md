# livedtranslate · 浏览器同声传译

![version](https://img.shields.io/badge/version-2.66.33-blue)
![license](https://img.shields.io/badge/license-MIT-green)
![manifest](https://img.shields.io/badge/Manifest-V3-orange)

一个 Chrome / Edge（Manifest V3）扩展：**捕获任意标签页正在播放的声音 → 实时语音识别 → 实时翻译 → 把双语字幕悬浮叠加在原网页上**。

看英文直播、听外语会议、刷没有字幕的生肉视频时，直接开它就行。原声照常从扬声器播出，字幕自动浮在画面上。

> 延迟模式下画面被推迟几秒，字幕就能提前准备好、和画面同步；播放页左上角有一个实时诊断面板，
> 会一直显示延迟、识别滞后、翻译耗时和缓冲状况。

```
标签页音频 ──► AudioWorklet(48kHz PCM) ──► 重采样 ──► 流式 ASR ──► 翻译 ──► 悬浮双语字幕
                     └──► 回放到扬声器（原声照旧可听）
```

---

## 字幕像熟肉，不像听写

这是它和大多数同传工具最直观的差别。

| | 常见做法 | 这里的延迟模式 |
|---|---|---|
| **字幕形态** | 中间结果**逐字往外蹦**，还会**回改** —— 先把听错的显示出来，识别修正后再覆盖一次 | **整句一次性出现**，原文和译文一起来 |
| **出现时机** | 说话过程中不断刷新 | **正好在主播张嘴那一刻** |
| **读起来像** | 实时听写的滚动条 | **看熟肉视频** |

### 为什么能做到：延迟不是缺点，是把等待变成了准备时间

延迟模式把画面推迟几秒。**于是当你看到主播张嘴的那一刻，这整句话其实早在几秒前就说完了** ——
识别早就出结果、翻译也早就回来了。字幕不需要边听边猜，可以在最合适的时刻**一次性、完整地**出现。

排期锚在这句**「开口」的时刻**，而不是「说完」的时刻。锚在「说完」，字幕要等画面播到这句结束、
**再等一整个延迟**才出来 —— 现象就是"人都快说完了字幕才上"；锚在「开口」，字幕就落在画面上人张嘴的那一帧。

前提是识别那边**一句话整段给出**，而不是逐字流式。本地 VAD 正是这样做的：它当场判断
"这句说完了"，然后把**完整的一句**交给 Whisper —— 所以延迟模式下不会出现中间结果，也就没有回改。

### ⚠️ 代价，得说清楚

- **画面比实况晚几秒**（推荐预设是 6.6 秒）。**这是它的工作原理，不是卡顿。**
- **只对延迟模式成立。** 叠加模式不推迟画面，就仍然是边听边出、会回改 —— 那是实时听写的形态。
- 延迟模式下**译文没赶上时字幕会先扣住不上屏，最多等 4 秒**；超过 4 秒就退回只显示原文，总比什么都没有好。

> 想更细地了解延迟模式为什么更准，见下面「延迟模式为什么更准：把延迟当"预习时间"用」。

## ⚠️ 先说清楚：音源差、说话快的时候，它会不准

**先讲优点、再讲边界 —— 这一节是边界。让你别调半小时参数才发现原因在哪。**

有两个**互相独立**的因素会显著拉低准确率，而它们**和扩展本身没关系** —— 是语音识别这件事本身的边界。

### 因素一：主播的麦克风差

Whisper 是在**以干净音频为主**的数据上训练的。遇到高底噪、频响窄、电平忽大忽小的输入，
它会明显掉点 —— 不是模型不够大，是**这类音频在训练数据里本来就少**。

**所以有个很值得做的对照实验：同一场直播换 Deepgram 再跑一次**（见「方案 A」）。
云端流式 ASR 的训练数据里有**大量电话级音质**，对这种音源通常明显更耐受。

- **换过去明显更准** → 问题在音源，不在本地方案。要不要为这一点付云端成本，你自己权衡。
- **换过去也一样差** → 音源本身超出了 ASR 的能力范围。**最有效的办法是让主播换个麦克风 —— 这个我们改不了。**

扩展这边能做的补偿有限（音频链里有高通、去直流、自动增益、限幅），最值得试的是
**把 AGC 档位调到「温和」**：提升上限从 +12dB 减半到 +6dB、收敛慢 4 倍。
差麦克风下默认档会把底噪一起放大，而且追得快的时候音量会来回"泵"，
而**断句和识别都讨厌电平忽大忽小**。

### 因素二：说话快

停顿变少变短 → 断句**没有可切的时机** → 段落被拉长。实测并到过 **6.1 秒 / 52 字**、
**8.5 秒 / 46 字** —— 这种长度读都读不完，而且一段里错一个字整句都受影响，
处理时间还随长度线性上升。

**对策：设置页「识别服务 → 本地 VAD」（或「阿里云百炼」）下面有语速档位，选「快语速」。**

**而这两件事会互相放大** —— 快语速下本来就容易漏字，差音源再雪上加霜。

### 值得先调的三个旋钮

| 旋钮 | 在哪 | 调成 |
|---|---|---|
| **语速档位** | 识别服务 → 本地 VAD（或阿里云百炼） | 快语速 |
| **AGC 档位** | 识别服务 → 音源质量（对所有识别服务生效） | 温和 |
| **画面延迟** | 设置页 | 调大（快语速每秒字数更多，识别和翻译都需要更多时间） |

> ⚠️ **「语速档位」和那几个断句旋钮在选「阿里云百炼」时同样在** —— 因为阿里也复用同一套
> Silero VAD 引擎切句，那些旋钮调的是**切句**，不是文本来源。所以选阿里时那个面板照样显示。
> 而 **AGC 档位对每一家识别服务都生效**（它改的是采集进来的音频本身），所以它放在服务商面板**外面**。

### 一句实话

**没有任何处理能把「差音源 + 快语速」完全修好。** 现实目标是"更好"，
不是"和干净音源一样"。

## 一、安装

无需构建，零依赖，直接加载：

1. 打开 `chrome://extensions/`（Edge 是 `edge://extensions/`）
2. 右上角打开 **开发者模式**
3. 点 **加载已解压的扩展程序**，选择本目录 `browser-lived-translate`
4. 首次安装会自动打开设置页

## 二、5 分钟跑通

### 方案 A′：阿里云百炼 Qwen-ASR（**国内直连，不需要代理**）

**如果你在国内、又不想折腾本地服务，从这一条开始。** 加它的原因很具体：
Deepgram 在国内要代理才能注册和使用，直接卡死了大部分用户。

1. 到 [阿里云百炼控制台](https://bailian.console.aliyun.com/) 创建 **DashScope API Key**
   （**官方免费额度：36000 秒 / 90 天**，按音频时长计费）
2. 扩展设置页 → **语音识别** → 识别服务选 `阿里云百炼 Qwen-ASR（国内直连）` → 粘贴 API Key
3. **翻译** → 翻译服务选 `Google 翻译（免 Key 通道）`，目标语言选 `简体中文`
4. 点「测试识别连接」看到成功提示 → 保存

**断句仍然在浏览器里做** —— 和「方案 B」用的是同一套 Silero VAD 引擎，
**所以选「阿里云百炼」时，那块 VAD 面板照样会显示**：「语速档位」和几个断句旋钮对它一样有效
（主播说话快就选「快语速」）。它们调的是**切句**，不是文本来源 —— 文本才来自阿里云。

> **默认模型是 `qwen-audio-3.1-asr-flash`。**
> 选 3.1 而不是 3.0，是因为 3.1 支持**原生文本润色**：模型在识别的同时会清理语气词与口吃重复、
> 处理说话过程中的自我纠正、理顺口语并规范标点。**它清洗的是翻译的输入** ——
> 喂给翻译的是理顺过的句子而不是「えーと、あの、その…」，**翻译质量会跟着上一档**。
>
> ⚠️ **老用户的设置里存着旧的 `qwen3-asr-flash`，不会被自动换掉。**
> 这是刻意的：改默认值只影响新装的人，不动已有配置（`getSettings()` 是"已存值盖在默认值上"）。
> **想用 3.1 请在设置页手动填一下。**
> 换模型名可能撞 404（两个端点认的模型不一样），保持「端点」在「自动」即可，扩展会自己选。

> ⚠️ **另外两件事先知道，免得后面被绕进去**：它**不是流式**（一句话说完才发出去，
> 延迟画面模式能盖住这点延迟）；而且它**没有** Whisper 那种置信度闸门。
> 两件的来龙去脉都在这节末尾。

#### 报错怎么读（401 和 404 的含义完全不同）

| 状态码 | 含义 | 该做什么 |
|---|---|---|
| **401 / 403** | **Key 无效**、填错了，或者不是这个地域的 Key | 去设置页核对 Key。**北京和新加坡的 Key 不通用** |
| **404** | **Key 是好的** —— 问题在模型名或端点 | 换回 `qwen3-asr-flash`，或把「端点」改成「自动」 |
| **429** | 额度用尽或频率超限 | 到百炼控制台的用量页看一眼 |
| **400** | 请求被拒 | 可能是模型名或音频格式；**刚填了提示词就先清空它**再试 |

**404 和 401 要分开看**：前者说明鉴权已经过了，别再折腾 Key。

阿里云有**两个接口，各认各的模型** —— 这是实测踩出来的：

| 端点 | 认哪些模型 |
|---|---|
| **兼容端点**（OpenAI 兼容） | `qwen3-asr-flash` ✅<br>`qwen-audio-3.1-asr-flash` ❌ → 404 `Unsupported model … for OpenAI compatibility mode` |
| **原生端点** | `qwen-audio-3.1-asr-flash`、`qwen-audio-3.0-asr-flash`、`fun-asr-flash-*`、`fun-asr`、`paraformer-v2` |

**所以「换个更好的模型名」不是改个字就行** —— 得连端点一起换。设置页里：

- **端点默认是「自动」**：模型名以 `qwen-audio-` / `fun-asr` / `paraformer-` 开头就走原生，其余走兼容
- **认不出的模型名会退回兼容端点** —— 那是更安全的一条（不会因为猜错端点而 404）
- 也可以强制指定，但**填错会报 404**，那时候看诊断面板里的原始错误

**⚠️「端点地址」那一栏留空是正常的，那才是正确用法。** 留空 = 按上面的规则自动选。
只有你需要填**业务空间专属域名**（形如 `https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/…`）时才用它。

> 早期版本的默认值就是那个兼容端点 URL，它会跟着设置一起存下来，
> 于是**老用户的「自动」永远被它盖住** —— 表现是填了 `qwen-audio-3.1-asr-flash` 却仍然收到
> `Unsupported model … for OpenAI compatibility mode`。
> v2.64.0 起：代码里「等于内置地址的 endpoint 一律当作没填」，并加了一条迁移把这种陈旧值清掉。
> **用户自己填的业务空间域名不会被碰。**

**提示词（上下文增强）两个端点都能用** —— 只是内部形状不同，扩展会自动按端点选对。

#### 热词（只在原生端点下有效）

填在设置页的「热词」那一栏，**每行一个**，`词` 或 `词:权重`：

```
切り抜き
草:5
スパチャ:50
```

- **权重 `1`~`5`**（官方推荐从 4 起试），**`50` = 超级热词**（召回率大幅提升，但全部超级热词加起来最多 50 个）
- 一个请求最多 **2000 个**热词，而且**免费**
- **规范**：含中文/日文等字符时**不超过 15 个字**；纯英文按空格切分**不超过 7 段**。
  超了扩展直接报中文错误，**不会静默丢掉** —— 静默丢掉会让你以为热词没用
- **⚠️ 兼容端点下热词无效** —— 那个端点的请求体里没有这个字段的位置。要用热词就得让模型走原生端点

#### 把内置术语表也用作热词

设置页里有一个勾选项 **「把内置直播术语表也用作识别热词」**（配置项 `asr.dashscope.glossaryHotwords`），**默认关闭**。

勾上之后，[内置直播词表](#内置直播词表默认开启)里的词会自动并进上面那个热词框。
那批词本来就是"主播真会念出来"的词 —— 当热词正合适，而且**你不用维护两份"我关心哪些词"**。

- **只取「源词 → 译文」的左边那一半** —— 热词提升的是**识别**，译文对识别毫无用处
- **你手填的热词不会被覆盖**：合并在前，同名词以你填的为准；总数上限 2000，超出的会在诊断里说明
- **内置词表里不合规范的词会被跳过**（比如超过 15 个字），并在诊断里报出跳过了几个 ——
  内置词表你改不了，为它报错也无从下手；但也**不会让它把整个请求拖成 400**
- **同样只在原生端点下有效**（和上面的热词框一样）

> 词表本身沿用翻译那边那两个开关（直播词表 / 游戏词表），**不另建一套**。
> 翻译想用哪些词，识别就用哪些词。

</details>

> ⚠️ **它不是流式。** 一句话说完才发给阿里云，比流式多一句的延迟 ——
> 延迟画面模式能盖住这个差距。**浏览器里做不了流式**：DashScope 的流式接口要求把 API Key
> 放在 **WebSocket 握手请求头**里，而浏览器的 `new WebSocket()` 设不了请求头
> （Deepgram / OpenAI Realtime 能直连，是因为它们官方支持用 subprotocol 传凭据）。
>
> ⚠️ 这个后端**没有** Whisper 那种 `no_speech_prob` 置信度闸门（阿里云不返回该字段），
> 所以只剩「空文本」和「幻听套话清单」两道闸门。
>
> ⚠️ **没有真实凭据做过联调。** 请求/响应结构是对着官方文档逐字段核对的，
> 但「服务端认不认」要你填上自己的 Key 才知道。第一次用如果报错，
> **把诊断面板里的原始错误贴出来**（401/403 = Key 无效或地域不对；429 = 频率超限或额度用尽）。

**第 1 步 · 下 whisper.cpp 的 Windows 包**

去 [whisper.cpp 的 releases 页](https://github.com/ggml-org/whisper.cpp/releases) 下载
**`whisper-bin-x64.zip`**（约 8.5 MB），解压到一个好找的地方，比如 `D:\whisper\`。

> **⚠️ 别只看最上面那个 "Latest"** —— 正式版本的附件列表**常常是空的**，
> 二进制挂在标着 **nightly** 的构建里（tag 是 `b5454` 这种纯数字）。
> 往列表下面翻，找带 `.zip` 附件的那一条。

**⚠️ 解压完 exe 不在最外层** —— 它在一个叫 `Release` 的子文件夹里，配套的 DLL 也在那儿：

```
D:\whisper\                 ← 你解压出来的目录
  └─ Release\               ← ★ 后面两步都在这一层里做
       whisper-server.exe
       ggml-base.dll · ggml.dll · SDL2.dll …（一堆 DLL）
```

**别把 exe 单独拖出来** —— 它要和那些 DLL 待在一起才能跑。后面说的"同一个目录"，
指的都是这个 `Release\`。

> **这段里哪些是验过的：**
>
> - ✅ **验过** —— 包里确实有 `whisper-server.exe`；它在 `Release\` 子目录里（不在根目录）；
>   文件名是 `whisper-bin-x64.zip`（约 8.5 MB）；包里自带 `ggml-base.dll` / `ggml.dll` / `SDL2.dll` 等一串 DLL。
> - ❌ **没验过** —— 我们没有真的在 Windows 上解压并启动过它，也没跑过第 3 步那条完整命令。
> - ⚠️ 自带那些 DLL **不等于"什么都不用装"** —— 启动时报缺 DLL 的话，装一次
>   [Microsoft Visual C++ 运行库](https://aka.ms/vs/17/release/vc_redist.x64.exe) 再试。
> - 万一下到的包里**没有** `whisper-server.exe`（只有 `whisper-cli.exe` 之类），
>   说明那个附件不含服务端 —— 换一个带 `.zip` 的 nightly 附件，或者退到下面折叠块里的 faster-whisper。

**第 2 步 · 下模型，放进 `Release\`**

**⚠️ whisper.cpp 不会自己下模型** —— 得你手动去拿。到 HuggingFace 的
[`ggerganov/whisper.cpp`](https://huggingface.co/ggerganov/whisper.cpp) 仓库下**一个** `.bin` 文件：

| 文件 | 大小 | 什么时候选它 |
|---|---|---|
| `ggml-large-v3.bin` | 约 2.9 GB | 质量最好，机器也够 —— **默认就下这个** |
| `ggml-large-v3-turbo.bin` | 约 1.5 GB | **不想等 2.9 GB 就用这个** —— 体积不到一半，质量接近 large-v3 |
| `ggml-medium.bin` | 约 1.5 GB | 同上，另一个选择 |
| `ggml-small.bin` | 约 466 MB | 只想先验证整条链路通不通 |

下好**放进 `Release\`**（和第 1 步那个 `whisper-server.exe` 放一起）——
这样下一步那条命令不用写一长串路径。

> **⚠️ 国内下 HuggingFace 常常很慢或者连不上** —— 慢的话看下面折叠块里的「国内下载模型」。
> 这一步**用浏览器下就行**，不依赖命令行联网。

**第 3 步 · 起服务**

**先进第 1 步那个 `Release\` 文件夹**，在里面打开命令行（在文件夹空白处**右键 →「在终端中打开」**，
或者按住 Shift 右键 →「在此处打开 PowerShell 窗口」），然后照抄这一行：

```bash
whisper-server.exe -m ggml-large-v3.bin -l ja --inference-path /v1/audio/transcriptions --host 127.0.0.1 --port 8080
```

> - **这个窗口别关** —— 关掉服务就停了。
> - `-l ja` 是日语；识别中文换成 `-l zh`。
> - **模型没放在 `Release\` 里**的话，`-m` 后面要写**你实际放它的完整路径**
>   （比如 `-m D:\models\ggml-large-v3.bin`），不是文件名。
> - **报「不是内部或外部命令」** → 多半是当前目录不对。敲 `dir whisper-server.exe`，
>   能列出来才说明你站在 `Release\` 里。
> - `--inference-path /v1/audio/transcriptions` 是**故意**加的：这个服务默认挂在 `/inference` 上，
>   而扩展要的是 OpenAI 兼容路径。加了它，下一步的地址才是 `/v1` 结尾。

**怎么知道服务起来了**：启动后那个窗口会打印加载模型的日志。**窗口不报错、停在那儿不动**就是起好了。
真正确认用下一步的「测试识别连接」—— **那个按钮会真的发一次请求**，比这里的任何说法都可靠。

**第 4 步 · 在扩展里填地址**

1. 设置页 → **语音识别** → 识别服务选 `本地 VAD 断句 + 本地 Whisper`（列表里第一项）
2. **服务地址**填 `http://127.0.0.1:8080/v1`
3. 点「测试识别连接」看到成功提示 → 保存

> **⚠️ 报「未找到文件」或者 404** —— 那是地址前缀多了一段或少了一段：
> 把 `/v1` 去掉再试一次（填 `http://127.0.0.1:8080`）。**两个都试一下就知道哪个对。**
> **这时候服务本身是好的**，不用去重装。

**断句仍然在浏览器里做** —— 和上面那个服务无关，用的是同一套 Silero VAD 引擎。
所以设置页那块 VAD 面板（「语速档位」和几个断句旋钮）对它一样有效，细节见本节后面。

#### 两种本地识别路线怎么选

`识别服务` 里还有一个 `OpenAI Whisper 分片（含本地）`，那是**固定时长切片**：不管有没有人在说话，
每 N 秒切一刀丢给 Whisper。**切口和句子边界无关** —— 一句话被从中间切开，
Whisper 就会把半句话脑补成一句完整的话。

**`本地 VAD 断句 + 本地 Whisper` 换了做法：**

```
音频 ──► Silero VAD（在浏览器里跑，ONNX）──► 只在「真的有人说话」的地方切
                          │
                          ├─ 静音确认（默认 450ms）→ 先出文本，但先不收句
                          └─ 收句静音（默认 900ms）或句末标点 → 收句
                                     ↓
                          切出来的一整句 ──► 本地 Whisper 出文本
```

两个好处：**切片落在句子边界上**（所以断句质量接近商用流式服务），
以及**没人在说话时一个请求都不发**（省 GPU，也少一半幻觉的机会）。

实测：**中位 18 字/句**（对照：商用流式服务 Deepgram 在同类内容上是 17.5 字），
单个分片的识别耗时 **0.03~0.09 倍实时** —— 8 秒音频只要 0.26 秒。

#### 就绪自检：跑不起来时会直接告诉你

启动时它会拿 `vendor/vad-selftest.wav`（一段 4 秒真人日语）把几种窗长**各跑一遍**，
把峰值概率报在诊断面板上，再挑能用的那个：

```
识别就绪 · 本地 VAD 自检通过 · 采用「640 窗」真人语音峰值 1.000（阈值 0.5）· Whisper @ ...
VAD · 其余变体：576 窗（v6）=1.000 · 640 窗=1.000 · 608 窗=1.000 · 512 窗（v5）=0.001
```

**为什么要这么麻烦** —— 见下面的⚠️。自检不过就不会假装"已就绪"，而是明确报不可用。

> ⚠️ **一个不看自检根本查不出来的坑：Silero VAD 的窗长。**
> 网上关于 Silero 的资料几乎一片倒地写「16kHz 用 **512**」，那是 **v5** 的参数。
> 而 `snakers4/silero-vad` 的 master 分支现在给的是 **v6 模型，窗长是 576**。
>
> 喂错窗长的症状极具迷惑性：**模型不报错、输出形状也对、输入电平完全正常，但概率恒为 0.001**
> —— 看起来就像"音频里没人说话"。
>
> 自检就是为此存在的：换模型版本时它会自己挑对，不用改代码。
> **自己换模型文件的话，记得看一眼诊断面板里报的峰值概率。**

#### 断句的四个旋钮（都在设置页）

| 旋钮 | 默认 | 作用 |
|---|---|---|
| **静音确认** | 450ms | **软边界**：静这么久就先出文本，但**先不收句**，跟后面拼 |
| **收句静音** | 900ms | **硬边界**：静这么久才算"这句真的说完了" |
| **最短话段** | 400ms | 短于它的当噪声丢掉，不单独出一条字幕 |
| **一句最长** | 5s | 说话人一口气讲很久时的强制切断 |

**「一句最长」旁边还有一个开关：**

| 开关 | 默认 | 作用 |
|---|---|---|
| **合理断句** | 开 | 到上限时**回头看最近约 1.5 秒**，找到一次换气就把切点挪过去 |

> 上面那个上限是**按时间**切的 —— 切点落在"第 5 秒时正在说的那个音"上，可能切在词中间，两边都缺字。
> 打开「合理断句」之后，8 秒的一口气会从 `5.0 + 3.0` 变成 `4.5 + 3.5`（切在一次换气上）。
> **找不到换气就完全和从前一样**（判据是"确实安静到不像人声"，和 VAD 用的是同一个阈值），
> 所以关掉它只是"回到从前"，不是修正什么。
> 开启后实际每段长度落在 **（上限 − 窗口）~ 上限** 之间 —— 上限设 8 秒就是 6.5~8 秒，
> **不会把你设的值改小很多**（窗口固定 1.5 秒封顶，只有上限小于 3.75 秒时才按 40% 缩小）。

> **调参方向**：字幕太碎 → 先把「收句静音」往上调（900 → 1400）。
> 字幕太长/太迟钝 → 把「静音确认」往回调（450 → 300）。
> 这两项**直接等于主要延迟**，别指望既能瞬间出字又不会切碎。

#### 语速档位：快语速和正常语速不是一套参数

**上面四个旋钮跟语速强相关**，而"这人说话快不快"你一眼就知道 —— 比让你去猜「静音确认该填 300 还是 450」直观得多。所以设置页最上面给了一个两档的下拉：

| 参数 | 正常语速（默认） | 快语速 |
|---|---|---|
| **静音确认**（软边界） | 450ms | **300ms** |
| **一句最长** | 5s | **3.5s** |
| **前后留白** | 200ms | **250ms** |

**为什么快语速要这么调：**

- **静音门槛必须更低。** 快语速的停顿本来就短（实测 200~400ms）。门槛还是 450ms 时，**这些停顿一个都不算数** → 句子只会越并越长，实测并到 **6.1 秒 / 52 字**、**8.5 秒 / 46 字** —— 读不完。
- **一句上限必须更小。** 每秒字数更多，同样 5 秒能攒出 50 字上下。
- **留白多给 50ms。** 快语速更容易切在音节中间，多留一点免得丢掉开头的字。

**选档位只是把一组数值写进上面那几个旋钮**（和「延迟预设」同一套机制），**之后仍然可以单独微调任何一个**；只要手改过，下拉就自动显示「自定义」，不会拿档位名骗你。全新用户默认落在「正常语速」，也就是一直以来的行为。

> **不知道选哪个？** 先按"听起来快不快"选一档跑几分钟，再看字幕：**出现 40 字以上的长句**就把「一句最长」再往下调；**一句话被切成两条**就把「静音确认」往上调 50~100ms。档位给的是起点，不是答案。

#### ⚠️ 识别结果会被质量闸门拦一部分

识别路径（和识别校正一样）会检查 Whisper 自己回传的置信度，不合格就**整段丢掉并报出来**：

```
VAD · 丢弃一段识别结果 · 判定为无人说话（no_speech_prob=0.74） · 原文「...」
VAD · 丢弃一段识别结果 · 命中幻听套话 · 原文「ご視聴ありがとうございました」
```

原因：Whisper 是在海量 YouTube 字幕上训练的，**在音乐/掌声/静音片段上会凭空吐出
「ご視聴ありがとうございました」这类片尾套话**。没有闸门的话，这种幻听会一路畅通地上屏、
还被翻译成「感谢您的观看」——看起来就像扩展在胡说八道。

判据是 `no_speech_prob > 0.6`、`avg_logprob < -1.0`、`temperature > 0`，
外加一份**只收最典型套话**的清单。清单刻意收得很窄 ——
「チャンネル登録お願いします」「おやすみなさい」这类**日语直播里真会说的话一个字都没收**，
因为杀掉真话比漏放几句套话糟得多。

#### ⚠️ 识别校正和 VAD 别同时开

两者都在做"把音频再识别一遍"这件事。用 VAD 时**把「识别校正」关掉**，否则等于白跑一趟。

### 方案 B'：OpenAI Whisper 分片（不推荐，留着备用）

同一个服务地址，但走固定时长切片。**只有在 VAD 那条路出问题时才用它** ——
分片时长默认 2 秒，调大更整但更慢，调小更快但更容易把句子切碎。

### 方案 C：OpenAI Realtime

设置页 → 识别服务选 `OpenAI Realtime 转写` → 填 OpenAI API Key → 模型选 `gpt-4o-mini-transcribe`。
> 浏览器 WebSocket 无法自定义请求头，扩展会先调 `/realtime/client_secrets` 换取短时密钥再连接；若该端点不可用会自动回退到直接用长期 Key 走 subprotocol。若因权限/地区原因连接失败，请改用方案 A。

## 三、界面与操作

### 两种呈现方式

弹窗顶部「呈现方式」二选一：

| 模式 | 做法 | 体感 |
|---|---|---|
| **字幕叠加在原页面**（默认） | 零延迟，直接在你的视频上叠字幕 | 字幕必然晚于画面 1–3 秒 |
| **延迟画面** | 另开一个播放页，把画面推迟 D 秒再放 | **字幕与画面同时出现**，而且能用最准的定稿翻译 |

延迟模式解决的是"字幕追不上画面"这个物理问题：画面推迟 D 秒之后，识别和翻译只要在 D 秒内完成就行。

### 延迟模式为什么更准：把延迟当"预习时间"用

叠加模式下画面是实时的，字幕必须一识别出来就翻，**没有任何余量**。
延迟模式推迟了 D 秒，这段时间可以花在两件事上：

```
|<---------------- D 秒 ---------------->|
|   等后文   |   翻译窗口   |
                      ↑
              固定 0.7 秒，没有旋钮
```

**翻译时机是一条固定规则：**

```
上屏时刻 at = 这句「开口」的音频位置 + 画面延迟
开始翻译   = at − 0.7s
翻译完了先等着，到 at 才上屏（没译文就扣住，见下文）
```

> **为什么不做成旋钮。** 这个值权衡的是「等后文」和「给翻译留时间」，但两边的代价完全不对称：
> 等多了只是少一点上下文，**留少了字幕就直接迟到**。这种东西不该让用户去猜。
>
> **0.7 秒是下限，不是死值。** 如果实测翻译比它慢，会自动往前让路
> （`max(0.7s, 实测 × 1.6 + 300ms)`，上限 4 秒）—— 否则就成了"翻译越慢越容易翻车"。
> 播放页底部会实时显示当前窗口和实测翻译耗时。

**1. 后文 —— 这是延迟独有的东西**

翻译时机是"**临上屏前才翻**"（而不是一识别出来就翻）。等到那时候，这句话**之后**的内容也已经识别出来了，
所以上下文里能同时给出【之前】和【之后】：

```
【之前】
we need to push mid right now
【之后】
their jungler is missing, care
```

指代、术语、语气都能对上，这是实时翻译做不到的。**画面延迟调得越大，能拿到的后文越多**——
播放页底部会实时显示「可用于等后文 ≈ X.Xs」。

**2. 复核校正（可选，仅 OpenAI）**

初译是"盲翻"的：模型看不到自己的输出，也没有回看的机会。开启「复核校正」后会再走一遍——
把原文和初译一起给它，只让它改术语、指代、数字这类确定的错误，并明确要求不润色。
代价是多一次调用，所以只有延迟模式会启用它。

**比换识别模型更有效的两件事**（都不用改代码）：

1. **源语言显式指定，别用「自动检测」。** nova-3 的自动检测实际走 `language=multi`，
   那是为语种切换设计的，单语种内容反而更差；而且这 10 种语言里**不含中文和韩文**。
2. **把术语表填起来。** 专有名词、游戏术语、人名——这是投入产出比最高的一步。

| 画面延迟 | 翻译窗口 | 可等后文 | 说明 |
|---|---|---|---|
| 5.0s | 0.7s | ≈4.3s | 翻译快的话就是这个 |
| 5.0s | 2.7s | ≈2.3s | 翻译实测要 1.5 秒时自动放开 |
| 2.0s | 0.7s | ≈1.3s | 延迟小，后文也少 |


### ⚠️ 时间到底花在哪了 —— 「句子没超过延迟」不等于来得及

一个常见的误解：**「延迟有 5 秒，句子才 3 秒，怎么会来不及？」**

因为**文本不是第 0 秒就到手的**。真正的时间线是：

```
音频位置 a ────────────────────────────── b
   │           人物在说这句话（L 秒）        │
   │                                        └─ +0.5s endpointing 判定"说完了"
   │                                        └─ +0.3s 网络/识别
   │                                        └─ +0.5s 识别校正（开了才有，实测 300~1100ms）
   │  文本到手 ≈ a + L + 0.8
   │                              └─ 翻译还要 X 秒（DeepL 实测 400~2000ms）
   └─ 画面上他张嘴的那一帧 = a + D
```

要字幕准时出现，必须：

```
句子长度 L + 0.8（断句判定 + 网络）+ 校正耗时 + 翻译耗时 X  ≤  画面延迟 D
```

**代入实测数字（断句 0.5 + 网络 0.3 + 校正 0.5 + 翻译 0.9 ≈ 2.2 秒）：**

| 画面延迟 | 能准时的最大句长 | |
|---|---|---|
| 5s | 2.8s | 大部分话都超 |
| 6s | 3.8s | 一般直播够用 |
| **8s** | **5.8s** | 大多数话都够（这也是界面上能调到的上限） |

**超过这个长度会怎样**：字幕不会消失，而是**一准备好就上屏** ——
那时句子还在画面上说着，只是不在他"开口那一帧"了。
所以观感是：**短句准点、长句偏晚**，而不是随机抖动。

> 诊断面板报的是**相对排期时刻**的偏差 —— 排期时刻 = 画面播到这句「开口」的那一刻，
> 所以 `now − at` 才是你感知到的量：
>
> ```
> 字幕上屏 · 比排期晚 0.62s · 这句说了 3.1s · 仍在句内
> ```
>
> **「仍在句内」= 晚得还没超过句长，观感可接受**（不报警）；
> 超过句长才会标红 —— 那才是真的需要处理。
>
> ⚠️ **别拿"相对实况"算滞后**：那会把画面延迟整个加进去。D=8 时报出「晚 8.6 秒」，
> 而实际只晚 0.6 秒。**换算口径用错会得出完全相反的结论** ——
> 会让人跑去调「画面延迟」，而真正该调的是「字幕同步微调」。

### 字幕为什么会**恒定偏早**：延迟测量少算了一段

延迟是这么测的：

```js
this.actualLagSec = bufferedEnd - video.currentTime;   // 缓冲末尾 − 播放头
```

而闭环纠偏的目标就是把它拉到 `delaySec` —— 所以这个数**恒等于你设的值**。

**但「缓冲末尾」不是「实况」：**

```
实况 ──[录音+编码固有滞后 L]──> 缓冲末尾 ──[你设的 D]──> 播放头
```

播放头离实况的真实距离是 **`D + L`**，而字幕排期用的是 **`D`**。
**所以字幕恒定偏早 `L`。**

分片是 `recorder.start(250)`，所以 `L` 至少是这个量级，再叠加编码器延迟。

**怎么处理：**

| 手段 | 说明 |
|---|---|
| **「字幕同步微调」调正值** | 直接把它抵掉，调一次固定。这是这个旋钮设计出来就是为了干的事 |
| **诊断面板** | 每 10 秒报一次 `延迟测量 · 缓冲末尾落后实况 0.35s` —— 看到这个数就知道该补偿多少 |

### 翻译窗口自动让路

固定窗口是 **0.7 秒**。但如果实测翻译比它慢，死守 0.7 秒就必然迟到 ——
那就成了「翻译越慢越容易翻车」。

所以实际窗口是：

```
max(0.7s, 实测翻译耗时 × 1.6 + 300ms)    上限 4 秒
```

| 实测翻译 | 实际窗口 | 效果 |
|---|---|---|
| 300ms | **0.7s** | 按固定规则走，剩下 4.3 秒照旧等后文 |
| 1500ms | **2.7s** | 自动让路，优先保证字幕准时 |

> 播放页底部会实时显示「翻译窗口 X.Xs（实测翻译 XXXms）」，不用猜。

### ⚠️ 改完「画面延迟」要等半分钟再看

**延迟靠「攒够 D 秒再起播」建立起来** —— 起播那一刻就把播放头放到 `缓冲末尾 − D`，
所以全新的延迟是**一步到位**的，不是慢慢爬上去的。

改「画面延迟」之后之所以还要等一会儿，是因为**画面本身还在按旧的时间轴走**：

**字幕排期会跟着一起爬** —— 每一拍（100ms）都按最新实测延迟重算排队中条目的上屏时刻。
但**别在刚调完的十几秒内判断准不准**，那时画面本身还在变。

| | 做法 |
|---|---|
| 实测延迟的更新频率 | 每一拍（100ms）都刷新，不用等下一句 |
| 排队中条目的上屏时刻 | **每一拍重算**，跟着画面走（不是算死） |

> 后者很关键：如果排队时把上屏时刻算死，**调整延迟之后字幕会集体提前**，
> 最大偏差正好等于你调的那个差值（5→7 就是 2 秒）。

> **调大延迟时**，播放头不会往回跳（已经看过的没法不看），所以实际延迟是**慢慢漂到**新目标的；
> **调小延迟**则会在下一次「延迟跳转」时一步到位 —— 见下一节。

### ⚠️ 延迟涨太多会跳一下 —— 这是故意的

**延迟模式里最容易出事的是「延迟只涨不落」。** 速率默认恒为 1（变速纠偏默认关着），
所以**涨上去的延迟没有任何机制把它拉回来**：播放头因为解码 4K60 偶尔卡顿、走得比实时慢，
而录制端是实时的 → 前方缓冲一路涨：

```
6.6s → 9.6s → 12.6s
12.6s × 78.6 Mbps ≈ 124 MB   →  撞穿 MSE 的内存配额
→ appendBuffer 失败 → 缓冲出现空洞
→ 播放头卡在空洞里 → readyState 2、缓冲见底、延迟涨到 21.7 秒、画面彻底停住
```

所以**前方缓冲**一旦超过「目标延迟 + 按码率算的余量」，播放头会**往前跳一次**，硬把延迟拉回目标，
并在诊断面板里说明：

```
延迟涨到 9.8s，已跳到目标 6.6s（跳过 3.2s 画面 —— 不跳的话会一路卡死）
```

**跳的阈值按码率算** —— 内存预算固定，码率越高、能容纳的前方缓冲越短，于是越早该跳：

| 场景 | 码率 | 涨到多少就跳 | 约合内存 |
|---|---|---|---|
| 4K60 高画质 | 79 Mbps | 9.6s | 约 90 MB |
| 4K30 高画质 | 64 Mbps | 11.6s | 约 89 MB |
| 1080p 标准 | 10 Mbps | 11.6s | 约 14 MB |

> **两害相权：画面跳一下，好过一路卡到彻底停住。**
>
> ⚠️ **如果跳得很频繁**（比如每分钟好几次），那说明**播放头持续跟不上解码** ——
> 这时的正解是把「采集帧率上限」降到 **30**，而不是继续修跳转。
> 4K60 的 H.264 解码对不少机器来说本来就吃紧，降到 30 帧基本就平了。

### 译文没赶上时，字幕会等 —— 不会先显示原文

**原文和译文是两回事**：识别一到手就有原文，翻译还要再花时间。

以前这两个时刻是脱钩的 —— 字幕到点就上屏，译文没回来就先显示**日文原文**，
过一会儿才变成中文。看起来就是「明明延迟有 5 秒，怎么上屏了还没翻译」。

现在**没译文就扣住不上屏**，等译文到了整句一起出现。但也不会无限扣：

| 情况 | 行为 |
|---|---|
| 译文正常回来 | 整句（原文 + 译文）一起上屏 |
| 译文晚了但最终回来 | 扣住等它，上屏时直接就是中文 |
| 译文超过 **4 秒**还没回来（挂了） | 退回显示原文，并在诊断面板报 `翻译没赶上 · 先显示原文` |

> 扣住的条目会**留在队首**，后面的不能越过它 —— 否则晚到的译文会插到已经上屏的字幕前面，顺序就乱了。
>
> 诊断面板还会报 `翻译完成 · 1500ms · 迟到 300ms（窗口只有 1200ms，把「画面延迟」调大）` ——
> **看到"迟到"就是窗口真的不够**：把画面延迟调大，或者换更快的翻译服务。

### 字幕怎么断句：一次完整的说话 = 一条字幕

Deepgram 在一次说话**中间**也会不断吐 `is_final` 分片。如果每个分片都当成一条字幕，
一句 15 秒的长句会变成七八条碎片一句句往外蹦 —— 读者看到的全是半截话。

延迟模式现在**只累积分片，到「说话人停下来了」才整句上屏**：

```
说话人开口
   ├─ is_final 分片 1  ┐
   ├─ is_final 分片 2  ├─ 只累积，不上屏
   ├─ is_final 分片 3  ┘
   └─ 安静超过 endpointing（默认 500ms）→ 认定「这句说完了」
          ↓
      整句一次上屏，**锚在这句「开口」的时刻 + D**
      —— 也就是画面正好播到他张嘴的那一帧
```

> ⚠️ **锚点是「开口」不是「说完」。** 这一点很关键：锚在「说完」的话，字幕要等画面把整句播完、
> **再补等一整个 D** 才出来 —— 现象就是「人都快说完了字幕才上」。锚在「开口」，
> 字幕就在画面上他张嘴的那一帧出现，并且一直留到下一句。
>
> 长句会超出延迟预算（`开口 + D` 早于文本到手），那时算出来的时刻已经落在过去，
> 排期层会**立刻上屏**——也就是「能多早就多早」，而不会再补等一个 D。

**「一句有多长」调 `endpointing`** —— **走 Deepgram 时**这是断句的主要旋钮
（走本地 VAD 的话换成「静音确认 / 收句静音」，而且**先选语速档位**再微调，见方案 B）：

| 信号 | 阈值 | 延迟模式 |
|---|---|---|
| `speech_final` | `endpointing`（默认 **500ms**，**可调**） | ✅ **主边界** |
| `UtteranceEnd` | `utterance_end_ms`（默认 1000ms，**Deepgram 硬下限就是 1000**） | ✅ 兜底（`speech_final` 没发时） |

```
调大 endpointing → 句子更长更完整，但可能把两句不相干的话并成一条
调小 endpointing → 更容易断开，但可能在换气处切成碎片
```

**两个阈值的脾气不一样，值得知道：**

1. **`endpointing` 是真正能调的旋钮。** 它决定「安静多久算说完」。设太小（比如 120ms）时，
   连换气（100~250ms）都会被判成「说完了」，长句碎成一片。句间停顿通常是 300~700ms，
   所以默认给 **500ms**。
2. **`utterance_end_ms` 调不下去** —— Deepgram 硬性要求 **≥1000ms**，
   所以它只能当兜底（`speech_final` 没发时用），别指望靠它缩短断句。

三个兜底（少任何一个都会出现「永远不上屏」）：

| 情况 | 兜底 |
|---|---|
| 说话人一直不停顿 | 累积跨度超过 15 秒就先上屏一次 |
| ASR 没发收句信号 | 最后一个分片之后静默 3 秒就上屏 |
| 停止采集 | 把没说完的一句吐出来 |

> 判定逻辑在 `lib/utterance.js`，独立模块、有 15 项单测 —— 因为这里很微妙
> （比如「没有时间戳时必须传 `undefined` 而不是 `null`」，否则会被当成时间 0、字幕排在过去立刻弹出）。
>
> **叠加模式不受影响**：它另有「中间结果翻译」保证出字速度，`endpointing` 抬高只让定稿晚 380ms。

### 识别校正：流式定时间轴 + 本地模型定文本

> ⚠️ **先看这条：走「本地 VAD 断句 + 本地 Whisper」时不需要开识别校正，两者别同时开。**
> VAD 那条路本身就已经是"切出一整句再送本地模型"，再做一次校正等于白跑一趟。
> 这一节说的是**用流式识别（Deepgram / OpenAI Realtime）时**的加成。

这是延迟模式最值钱的一项 —— **画面推迟的这段时间里，音频还留着**，可以拿它重新识别一遍。

**分工是固定的，两边互不干扰：**

| | 谁来做 | 决定什么 |
|---|---|---|
| **时间轴** | 流式识别（Deepgram） | 字幕**什么时候**上屏 —— `start` / `duration` 驱动排期 |
| **文本** | 本地模型重识别（whisper.cpp 等） | 字幕**写什么** |

所以重识别失败、超时、服务没起、或者干脆没配，**都不会动到字幕的时序**，只是没拿到那份加成。

```
收句（speech_final）
   ├─ 立即排期上屏（用流式文本先兜着，时序已锁定）
   └─ 同时把这一段音频丢给本地模型重识别
           ↓ 约 0.5 秒（RTX 5080 + large-v3）
      覆盖文本 → 翻译时用的是校正后的文本
```

**为什么这样更准**：流式识别为了压低延迟，必须不停下判断、随时准备断句，代价就是准确率。
非流式接口拿到的是**完整的一段话**，可以前后通看，还能开标点与大小写规整。

#### ⚠️ 但不是无条件采用 —— 有置信度闸门

**本地模型听错时，无条件覆盖会把流式本来听对的也一起盖掉**，结果比不做校正还差。

所以重识别走 `response_format=verbose_json`，用它回传的置信度判断"这次是不是在编"。
判据就是 Whisper 自己用的那两个：

| 信号 | 含义 | 阈值 |
|---|---|---|
| `temperature > 0` | 解码被判失败后**回退到高温重试** —— 幻觉最典型的来源 | 任何 > 0 |
| `no_speech_prob` | 这段本来就没人在说话（音乐、音效、静音） | > 0.6 |
| `avg_logprob` | 模型自己都没把握 | < −1.0 |

任何一段不合格 → **弃用这次校正、沿用流式文本**，并在诊断面板说明原因：

```
识别校正弃用 · 412ms · 解码回退到 temperature=0.4（沿用流式文本）
识别校正 · 523ms · 18 字 · 置信 -0.35
```

> 拿不到置信度时（比如某个中间层只支持 `json`）也一律按"不可信"处理 —— **宁可不用，也不盲信**。
>
> `verbose_json` 是实测确认的：whisper.cpp 与 faster-whisper 都支持，每个片段带
> `avg_logprob` / `no_speech_prob` / `temperature`，还有逐词 `probability`。

#### ⚠️ 提示词默认是空的 —— prompt 更容易把 Whisper 带偏

旧版会把 `translate.glossary`（翻译术语表）和内置词表一起拼成 prompt 发出去。
结果是一堵**英文**直播术语被拿去识别**日语**音频：

```
charity stream members-only members only waiting room memberships
subscribers live stream super chat superchats membership gifted sub
subscriber moderators livestream graduation
```

同一段真实日语，在同一台机器上实测（whisper.cpp + large-v3）：

| prompt | 结果 | |
|---|---|---|
| **不加** | `そうなんだよね / ティールで一瞬で流れたりするからね / あれピンクと黒の髪の毛の色はあれひなのじゃん` | ✅ 全对 |
| 那堵英文 | 丢了开头、多出「目立ち」 | ❌ |
| 日文相关词 | 仍丢掉第一句，还把「ひなの」听成「ひなうの」 | ❌ |
| 很短且无关的英文 | 三行被拆成四行 | ⚠️ |

**prompt 从来没有把结果变得更好，只是变差或持平。** 所以现在：

- **默认完全不发提示词**
- **翻译术语表不再参与识别** —— 它是给翻译用的，管术语一致
- 识别偏置只认两处**显式为识别填的**字段：`asr.refine.prompt` 与 `asr.deepgram.keyterms`
- 提示词仍按**字符数**封顶（Whisper 的 prompt 只有 224 token）

**怎么开**：设置页 → 识别校正 →「开启」。**默认是关的**，而且它用的是
`asr.whisperChunked.baseUrl` —— 那个地址必须真的指向一个在跑的服务。

> **默认关着是有原因的，自己开之前先知道这三件事：**
>
> | 设计取舍 | 为什么 |
> |---|---|
> | **默认关** | `baseUrl` 默认指向 `127.0.0.1:8000`。没跑服务的人如果默认开着，每句都会打一次空请求 |
> | **提示词按字符数封顶（180）** | Whisper 的 prompt 只有 224 token，超了它会开始复读或胡编。Deepgram 的 `keyterm` 同理限 30 条 |
> | **超时 2.5 秒；连续失败 2 次自动暂停 30 秒** | 服务没起时不该让每句都全量等一次超时 |
>
> 它和 VAD 那条路是**二选一**：VAD 本身就已经在"切一整句送本地模型"了，两个一起开等于白跑一趟。

**它只作用于延迟模式。** 叠加模式手里没有留存的音频，用不上。

- 原标签页会被 **tabCapture 自动静音**（固有行为），顶部会出现一条可关闭的提示（12 秒后自动收起），里面的按钮可跳到播放页
- 播放页底部能调 **画面延迟**（0.5–8 秒）、**字幕同步微调**（±2 秒）
- 延迟值要 ≥「整句识别完 + 翻译往返」的总时间。识别约 0.4s，但**还要等说话人停顿**
  （`endpointing` 默认 500ms）才算一句说完；Google 免 Key 翻译约 0.2–0.5s —— **3–5 秒是稳妥的区间**
- 代价：多一个标签页、需要重新编码（1080p 约多 10–25% CPU）、**DRM 内容不可用**
- **画质档位**（设置页 → 延迟画面画质）：省资源 ×0.5 / 标准 ×1.0 / 高画质 ×1.6 / 极致 ×2.4，
  另有**采集帧率上限**（默认 60）。⚠️ 这两项**改了要重新开始才生效**，播放页会提示 ——
  它们在启动时就烘进了编码器和采集约束，中途改不了。详见下一小节
- 播放页由扩展程序打开，本身没有用户手势，浏览器可能拒绝带声音的自动播放；真被拒时页面会显示一个**「开始播放」按钮**，点一下即可
- 原理与边界见 [docs/delayed-playback.md](docs/delayed-playback.md)

#### 为什么会有「画质档位」这个东西

延迟画面要把画面**重新编码一遍**，而重编码的码率决定了运动画面糊不糊。

衡量"够不够"的通用指标是 **bpp**（每像素每帧位数）—— 同样是 4 Mbps，
1080p 够用、4K 就严重偏低。偏高时的症状很好认：**静止画面还凑合（帧间几乎没变化），
一运动就糊**，因为编码器只能丢掉细节去凑那个码率。

| bpp | 观感（4K30 下对应的码率） |
|---|---|
| 0.16 以下 | 静止够，**一运动就糊**（40 Mbps） |
| 0.26 左右 | 运动画面干净（64 Mbps） |
| 0.39 左右 | 基本看不出二次压缩（96 Mbps） |

所以码率**按画面尺寸自动估**（基准"1920×1080@30 → 10 Mbps"线性外推），再乘档位倍率。
H.264 效率低于 VP9/AV1，所以它需要的码率更高。按尺寸估的好处是**换分辨率不用重调**。

> ⚠️ **采集帧率上限（默认 60）**是另一个容易白丢一半的地方：不显式给的话，
> Chrome 对标签页采集常只给 **30fps**，源本身是 60fps 时运动画面就发顿。
> 它是**上限不是强制值**，源只有 30fps 时没有副作用。
>
> ⚠️ 但帧率翻倍会让**自动码率也跟着翻倍**（保持同样的 bpp）：4K30 高画质 ≈ 64 Mbps，
> 4K60 ≈ 128 Mbps。如果变卡，先把画质档位降一档。
>
> ⚠️ 画质和帧率**改了要重新开始才生效**，播放页会提示 ——
> 它们在启动时就烘进了编码器和采集约束，中途改不了。

| 位置 | 说明 |
| --- | --- |
| 扩展图标弹窗 | 开始/停止、呈现方式、延迟秒数、实时音量条、**识别/翻译耗时读数**、目标语言、字幕位置、字号、静音原声、显示原文、显示诊断信息、最近字幕、复制/清空 |

### 为什么音频处理放在 offscreen 而不是 service worker

MV3 的 service worker 空闲约 30 秒就会被回收，WebSocket 长连接和定时任务放里面必然断。
offscreen document 只要不被显式关闭就持续存活，所以：**音频采集、ASR 长连接、翻译请求、翻译缓存全部在 offscreen**；
service worker 只做轻量编排，被回收后由消息重新唤醒也不影响正在进行的识别。

## 六、准确率是怎么抠出来的

同传的字幕质量 = 识别准确率 × 翻译连贯性。下面这几处是专门为"直播场景 + 准确率优先"做的。

### 1. 抗混叠（影响最大的一处）

之前 48kHz → 16kHz 用的是 3 点盒式平均降采样，它本质是个很差的低通：**8kHz 处只有 −3.5dB、9.6kHz 处 −5.5dB**。直播里的观众噪声、音乐、音效富含 8–24kHz 能量，会被折叠（混叠）回 0–8kHz 的语音频段，直接污染识别输入。

现在换成 **8 阶 Butterworth（4 个 biquad 级联，截止 0.44 × 目标采样率）**，实测阻带抑制：

| 频率 | 盒式平均（旧） | 8 阶 Butterworth（新） |
|---|---|---|
| 8 kHz | −3.5 dB | **−10.9 dB** |
| 9.6 kHz | −5.4 dB | **−26.5 dB** |
| 12 kHz | −9.5 dB | **−48.7 dB** |
| 16 kHz | 有零点但不单调 | **−86.8 dB** |

通带几乎无损（3kHz 处 −0.00dB，6kHz 处 −0.23dB）。滤波器全部用 Web Audio 原生节点实现，**零 JS 开销**——如果手写 FIR 要多烧大约 5% 的一个核。

### 2. 去直流 / 低频隆隆声

分析支路最前面加了 80Hz 二阶高通。空调声、桌面震动、电流声这类能量对识别没有帮助，却容易让服务把整段判成有声音。20Hz 处 −24dB，200Hz 以上几乎无影响。

### 3. 安静音源自动增益

直播里说话人偏轻、页面音量本身很小的情况很常见，识别率会明显掉。分析支路带一级 AGC：**只提升、不衰减**（增益范围 1～4，即最多 +12dB），低于噪声门时冻结（不放大底噪），后面再跟一级 −6dB 阈值限幅器防止突然的大声过载。

"只提升不衰减"是刻意的——用户现在的听感就是下限，最坏情况不会比不开更差。放大后的电平也会实时反映在弹窗的音量条上；如果连 +12dB 都拉不起来，弹窗会提示音源电平过低。

#### ⚠️ 但 AGC 是双刃剑 —— 所以给了四档

**它的本意是把忽大忽小的音量拉平（对识别有利），可追得太快就会在音量起伏时来回"泵"** —— 而 VAD 和 Whisper 都讨厌电平忽大忽小。**差麦克风下更麻烦**：+12dB 的上限会把底噪一起放大，等于把噪声也"提"成了有效信号。

设置页的 VAD 面板里可以选档位：

| 档位 | 提升上限 | 噪声门 | 增益收敛 | 目标电平 |
|---|---|---|---|---|
| 关闭 | ×1 | 0.0025 | — | — |
| **温和**（差麦克风推荐） | **×2（+6dB）** | **0.006** | **1.5s** | 0.07 |
| **标准**（默认） | ×4（+12dB） | 0.0025 | 0.35s | 0.09 |
| 强力 | ×6（+15.6dB） | 0.002 | 0.25s | 0.12 |

**「温和」针对的就是上面那两件事**：提升上限砍半（底噪不会被放大那么多）、收敛慢 4 倍（音量起伏时不会来回追）、噪声门抬高 2.4 倍（更不容易把底噪当信号）。

> **默认仍是「标准」** —— 也就是一直以来的行为。**音源本来就正常就不用动它。**
> 觉得识别在音量起伏时发抖、或者主播的麦克风明显发闷有底噪，再试「温和」。

> 整条分析链路（高通 → 抗混叠 → AGC → 限幅）**只挂在送识别的支路上**。`source → playbackGain → destination` 完全并行、不经过任何处理，你听到的原声不受影响。

### 4. 翻译上下文

逐句独立翻译会丢掉代词指代、省略主语和术语一致性。现在定稿翻译会把**前面 N 句原文**一起发给翻译服务：

- **OpenAI**：放进 system 消息，明确标注"仅供理解指代，不要翻译、也不要重复"
- **DeepL**：用官方的 `context` 字段（它就是为"影响译文但不被翻译"设计的）
- **Google 免 Key 通道**：该通道没有这个能力，自动跳过

上下文窗口由「翻译上下文句数」控制（默认 2，上限 600 字符），不会无限膨胀。

### 5. 术语表（专有名词、游戏用语译错就靠它）

先分清是**识别错**还是**翻译错**——开着「显示原文」时字幕上有两行：

| 现象 | 问题在哪 | 怎么修 |
|---|---|---|
| **原文就错了**（识别成了别的词） | 语音识别 | Deepgram 的「关键词表」（nova-3 的 `keyterm`），或把「音频语言」指定准确 |
| **原文对、译文错** | 翻译 | 术语表（下面这一节） |

术语表每行一条 `原文=译文`，**对所有翻译服务生效**，但各家的落地方式差别很大：

| 翻译服务 | 落地方式 | 可靠性 |
|---|---|---|
| **DeepL** | 官方 glossary API：自动创建术语表、缓存 id、内容变了自动重建 | **最可靠**，DeepL 保证遵守 |
| OpenAI / **DeepSeek** / **Ollama** | 写进系统提示词 | 模型会尽量遵守，不是硬保证 |
| Google 免 Key 通道 | 占位符替换：把术语换成标记送过去，回来换回目标词 | **best-effort**，翻译器偶尔会吞掉标记 |
| 百度翻译 | 写进翻译请求的 `q` 之前做占位符替换（同 Google 那条路） | best-effort |
| 腾讯云 / 阿里云机器翻译 | **不生效** —— 这两家的适配器只做了基本翻译，没接术语表 | — |

> ⚠️ **腾讯和阿里目前不支持术语表。** 它们的接口本身也没有 glossary 能力，要支持得走和 Google
> 一样的占位符替换那条路（改造点在 `lib/translate/index.js` 的 `translateTencent` / `translateAli`）。
> 需要的话可以加，但**目前填了术语表对这两家没有任何效果**。

> ⚠️ **DeepL 不允许在「源语言 = 自动检测」时使用术语表。** 想用术语表就必须在设置页把源语言指定成具体语言。
> 真发生这种情况会通过页面诊断面板明确提示，不会静默失效。

| **百度翻译** | ✅ | 国内直连不需要代理。⚠️ **免费版 QPS=1**（每秒一次），同传的中间结果刷新容易撞 54003 限流 |
| **腾讯云机器翻译** | ✅ | 国内直连。每月有免费额度。需要 SecretId / SecretKey，**并且必须填地域 Region**（腾讯云 API 要求声明地域）。 |

**两家国内云服务要填什么：**

| | 设置页里填 | 去哪拿 |
|---|---|---|
| **腾讯** | SecretId、SecretKey、**地域**（默认 `ap-guangzhou`） | [控制台 → 访问管理 → API 密钥](https://console.cloud.tencent.com/cam/capi) |
| **阿里** | AccessKeyId、AccessKeySecret | [RAM → 访问控制 → 密钥](https://ram.console.aliyun.com/manage/ak) |

> ⚠️ **阿里的语种代码里，繁体是 `zh-tw`（全小写）**，和别家的 `zh-TW` 不一样。两张映射表都在
> `lib/translate/index.js`（`TENCENT_LANG` / `ALI_LANG`），**没映射到的语种会直接抛中文错误，
> 不会静默透传** —— 透传的后果是服务端只回一句"语种不支持"，用户根本看不出是自己选的语言不在列表里。
>
> ⚠️ **腾讯的语言代码表没有从官方逐条核对过**（腾讯云文档站的语言代码页始终跳回目录页）。这里按
> 该接口的通行约定（ISO-639-1）实现，所以配了「没映射就报错」这条兜底。如果你遇到报"语种不支持"，
> 把具体语种告诉作者。
>
> ⚠️ **两家的签名算法都对官方示例向量做过逐位验证**（腾讯的 TC3-HMAC-SHA256、阿里的 POP
> HMAC-SHA1+Base64，见 `tools/smoke-test.mjs`），但**没有真实凭据做过端到端实测** ——
> 签名之外的部分（请求头、参数）是按官方文档写的。第一次用如果报错，把诊断面板里的原始错误贴出来。
>
> ⚠️ 阿里建议用 **RAM 子账号**的密钥，只授予 `AliyunMTFullAccess`，别直接用主账号的。

> **DeepSeek 和 Ollama 之所以能"免费"接进来**，是因为它们都实现 OpenAI 兼容协议 ——
> 扩展里三者**共用同一套请求代码**，只差默认地址与模型名。想再加一家（月之暗面、智谱、硅基流动、
> 自建 vLLM…）只要往 `lib/translate/index.js` 顶部那张表加一行。
>
> 而**百度 / 腾讯 / 阿里这三家各有一套签名**（MD5、TC3-HMAC-SHA256、POP HMAC-SHA1），
> 没法共用代码，只能各写一份。三家的签名原语都在 `lib/crypto.js`，
> 且**都有测试向量钉着** —— 签名算错了服务端只会回一句"签名不匹配"，没有别的线索。
> 腾讯和阿里用的是**官方文档里的示例向量**，不是自造的回归值。

### 6. 默认对中间结果也做翻译

「也翻译中间结果」**默认开启**。这是同传体感最大的一个开关：

- **开启**：识别一出中间结果就送去翻译，字幕几乎立刻有译文；代价是译文会随识别修正而刷新（看着会"跳"）。
- **关闭**：只在句子定稿后翻译一次，译文最稳；但定稿时机由识别服务的模型判断，说话人不停顿时可能等很久才有中文。

想要后者可以在设置页顶部切到「准确优先」预设。

### 7. 绕开 smart_format 的 3 秒定稿挂起

Deepgram 官方文档（[Smart Formatting](https://developers.deepgram.com/docs/smart-format)）写明：流式场景下遇到"疑似不完整的实体"（数字、日期、货币、电话号），系统会**等说话人继续说话，或者静默 3 秒后才定稿**。对逐句翻译的管线来说这是致命的。

扩展默认 **`smart_format=false`**，只损失数字/日期/货币的规整（中文场景收益本来就低），标点仍然由 `punctuate=true` 提供，不受影响。需要规整就切到「准确优先」预设。

### 8. 识别滞后读数

弹窗里显示的 **「识别 X.Xs」** 用的是 Deepgram 官方推荐的算法：拿结果覆盖到的音频时间点，对比已经送出的音频时长。官方特别强调**只用中间结果**算——定稿还额外包含"说话结束检测"的等待，混进去会把这个数字算大、失去定位价值。扩展正是这么实现的。

配合「翻译 Y.Ys」一起看，就能一眼看出慢在哪一段。详见第七节。

## 七、太慢怎么办（延迟排查）

**先看数字，别猜。** 有两条**互相独立**的通道能看到同样的数字，可以互相印证。

### 通道 A：弹窗

```
识别 0.4s · 翻译 0.25s
```

- **识别** = 识别结果覆盖到的音频时间点，对比"已经送出的音频时长"。这是 Deepgram 官方推荐的算法（只用中间结果算，因为定稿还额外包含"说话结束检测"的等待）。正常值 **0.2–0.6 秒**。
- **翻译** = 翻译接口的往返耗时。Google 免 Key 通道正常 **0.1–0.4 秒**；OpenAI 约 **0.4–1.5 秒**。

### 通道 B：页面上的诊断面板

**默认开着**，不用勾任何东西。只要开始同传，**字幕上方**就会出现一个面板，第一行是版本号：

```
livedtranslate v2.66.33 · 字幕层就绪
识别 0.4s · 翻译 0.25s
翻译完成 · 312ms · google-free
```

每次翻译的开始 / 完成 / 失败也会打到**页面控制台**（在视频页按 F12 看 `[livedtranslate] ...`）。
另外内容脚本在**每个页面加载时**都会无条件打一行 `[livedtranslate] 字幕层已加载 · v<版本>`——
**看不到这一行，就说明页面上跑的不是这个构建**，其它都不用查了。

不想要面板就去弹窗里取消勾选「显示诊断信息」。

两条通道走的是**完全不同的路**：

| | 路径 |
|---|---|
| 弹窗 | offscreen → SW → `chrome.storage` → 状态广播 → 弹窗 |
| 诊断面板 | offscreen → SW → `chrome.tabs.sendMessage` → 页面（**和字幕同一条路**） |

**所以它可以当判据用：**

| 现象 | 结论 |
|---|---|
| 面板有数字、弹窗没有 | 问题在**状态通道**（storage / 广播），翻译本身是好的 |
| 两边都没数字，但面板里有「翻译开始」 | 请求发出去了但没回来——超时、限流或被墙 |
| 面板里是「翻译失败 · … · HTTP 403」 | 翻译服务的 Key / 套餐 / 网络问题，错误原文直接写在面板上 |
| 连面板都出不来 | **页面上跑的不是这个构建**（见下），或字幕层没注入 |

#### 「改了代码但没生效」这个陷阱

**这是个 MV3 的平台特性，不是扩展的 bug：** 扩展**重新加载**后，已经打开的页面里的旧内容脚本
会被废掉（context invalidated），但它在 `window` 上留下的任何"我已注入"标记**仍然在**。
所以字幕层不能用布尔标记判断自己是否已加载 —— 新脚本一进来看到标记就 `return`，
页面上就再也没有可用的字幕层，看起来就像"改动没生效"。

这个扩展**按版本判断**：同一版本重复注入才跳过；版本不同就接管。
SW 的 `ensureContentScript` 也会比对 PING 回来的版本，不一致就重新注入。
所以 **重新加载扩展后不必刷新页面**，下次开始同传时会自动换成新字幕层。

> 排查时先看控制台有没有 `[livedtranslate] 字幕层已加载 · v<版本>`。
> **版本的这一行是判断"页面上跑的是不是当前构建"最快的办法。**

没测出来的一侧显示 `—`（而不是整段消失），这样你分得清"还没测到"和"没这个功能"。

哪个数大就治哪个。

### 如果「识别」很大（> 1.5s）

| 原因 | 处理 |
|---|---|
| **`language=multi`** | 源语言明确时一定显式指定。「自动检测」在 nova-3 上走 `language=multi`，只覆盖英/西/法/德/印地/俄/葡/日/意/荷 **10 种语言，不含中文和韩文**；而且社区多次报告它建连明显更慢。设置页选实际语言。 |
| 网络到 `api.deepgram.com` 远 | 换网络/代理节点。官方给的网络传输典型值是 20–200ms，超过就是链路问题。 |
| 用了 Whisper 分片 | 分片模式延迟 = 分片时长 + 推理时间，默认 5 秒就意味着至少 5 秒。调到 2–3 秒，或换 Deepgram。 |

### 如果「翻译」很大（> 2s）

| 原因 | 处理 |
|---|---|
| 用了 OpenAI/DeepL 翻译 | 换「Google 翻译（免 Key 通道）」，明显更快。 |
| 翻译上下文太长 | 「翻译上下文句数」调小或调 0。 |
| OpenAI 模型太大 | 换 `gpt-4o-mini`。 |
| 翻译服务限流或本身变慢 | 扩展已做背压与超时（见下），剩下就是服务商侧的往返时间。 |

### 「识别很快，但整句识别完之后翻译迟迟不来」

这是**翻译请求在排队**的典型症状。

浏览器对同一个域名只有 6 条并发连接（HTTP/1.1）。如果中间结果翻译没有背压，请求一慢就会不停堆积，
**定稿翻译——也就是你真正在等的那一条——被排在一堆已经过时的中间结果请求后面**。
更糟的是，如果这些请求全都堵着不返回，就没有任何一次翻译耗时被记录下来，
弹窗里的「翻译」会一直显示成 `—`。

扩展现在保证：

- 同一时刻**只有一条**中间结果翻译在飞；期间新到的文本只覆盖待办，前一条结束再用最新文本发
- **定稿翻译会立刻取消在飞的中间结果翻译**，把连接让出来
- 单次请求 **12 秒没响应就放弃**并给出可读错误，不再无限挂起
- 被抢占的中间结果不会误报成「翻译失败」

### 如果两个数字都不大，但字幕就是不出来

那瓶颈在**定稿**，不在识别或翻译。按可能性排序：

1. **「也翻译中间结果」被关掉了**（设置页 → 翻译）。这是最常见的原因。关掉后译文只在句子**定稿**时才出现，而说话人一直不停顿的话，你要等很久才看到中文。**默认是开的**，如果你手动关过，打开它。
2. **开了 `smart_format`**。Deepgram 官方文档原文：流式场景下遇到"疑似不完整的实体"（数字、日期、货币），系统会「等说话人继续说话，**或者静默 3 秒后定稿**」。做实时字幕必须关掉它——扩展已默认关闭，标点由 `punctuate` 单独提供，不受影响。
3. **`endpointing` 太小**。它决定「安静多久算说完」（也是延迟模式的句子边界）。Deepgram 默认值只有 10ms，会把句子切得极碎。扩展默认设成 **500ms**（句间停顿通常 300~700ms）。**注意：调小它会切碎，调大它会并句** —— 这是同一个旋钮的两面。
4. **说话人长时间不停顿**。识别服务的 `is_final` 什么时候来由模型判断，官方没有给任何周期承诺。扩展加了「强制断句上限」（默认 10 秒）：到点会先给识别服务发 `Finalize` 请它立刻冲刷缓冲区拿一份真定稿，**700ms 内没回执就本地兜底**。所以最坏情况下你的字幕也不会卡超过 ~10.7 秒。

### 四个预设

设置页最上面有一键预设，不想逐项调就用它。**注意它们是两类东西：**

**「推荐」装的是整套方案**（识别服务、语言、服务地址、翻译服务、目标语言、呈现方式、画质、帧率）：

| 预设 | 内容 |
|---|---|
| **推荐（本地模型 + 延迟画面）** | 本地 VAD 断句 + 本地 Whisper + DeepL 翻译 + 延迟画面 6.6s + 高画质 60fps |

> ⚠️ **套用它之前会弹一次确认，逐条列出会改哪些设置。** 这是刻意的：
> 一个看英文直播、用 Google 免 Key 翻译、叠加模式的用户，如果顺手点了下拉里第一项，
> 会在毫不知情的情况下被换成"日语 + DeepL（没配 Key）+ 延迟模式"——
> 翻译全挂、原页面还被静音。而且下拉是**改完立刻写盘**的，连保存按钮都不用点。

**其余三个只管延迟旋钮**（翻译时机、Deepgram 断句门槛）：

| 预设 | 中间结果翻译 | 最短字数 | 翻译间隔 | 上下文句数 | endpointing | smart_format | 体感 |
|---|---|---|---|---|---|---|---|
| **速度优先**（默认） | ✅ | 4 | 400ms | 2 | 500 | 关 | 字幕几乎立刻出译文，但会随识别修正刷新 |
| 均衡 | ✅ | 6 | 600ms | 2 | 650 | 关 | 比速度优先多约 0.3–0.5s，跳动更少 |
| 准确优先 | ❌ | 10 | 900ms | 3 | 800 | 开 | 译文最稳不跳动，但说话人不停顿时会等很久 |

> 手动改过任意一项，下拉框会显示成「自定义」，改动仍然生效。
>
> ⚠️ **下拉框的显示用的是"懂事版"的判定**（`detectPresetForUi`，不是 `detectPreset`）。
> 原因是两类预设回答的是**不同问题**：你套用了「推荐」之后只把翻译服务改回 Google，
> 延迟旋钮那六项仍然匹配「速度优先」，于是下拉会显示成「速度优先」——
> 而那个标签描述的是延迟旋钮，跟你实际的识别/翻译/呈现选择毫无关系。
> 现在这种情况会老实显示「自定义」。

### ⚠️ 老用户必读：改默认值对已用过的用户无效，但迁移会生效

`getSettings()` 是「已保存的设置」盖在默认值上。而弹窗/设置页只要你动过任何一个控件，就会把
**当时那份完整设置**整体写回本地存储——包括当时的默认值。所以**光改代码里的默认值，对已经用过的用户完全无效**。

为此加了设置版本号（`SETTINGS_VERSION`，当前 **6**）和迁移表。升级后第一次读取设置时自动迁移，
规则是**只在该项仍然等于旧默认值时才覆盖**（说明你从没主动改过它），你明确设置过的值一律保留。

历史上迁移过的项：

| 版本 | 项目 | 旧默认 | 新默认 | 原因 |
|---|---|---|---|---|
| v2 | 「也翻译中间结果」 | 关 | **开** | 关掉后译文要等定稿，说话人不停顿会等很久 |
| v2 | 中间结果最短字数 | 10 | 4 | 门槛太高会拖慢首次出字 |
| v2 | 中间结果翻译间隔 | 900ms | 400ms | 同上 |
| v2 | `endpointing` | 300 | 120 | 缩短定稿等待（v4 又抬回去了） |
| v2 | `smart_format` | 开 | **关** | 官方说明最多 3 秒定稿挂起 |
| v3 | 术语表位置 | `translate.openai.glossary` | `translate.glossary` | 原来只对 OpenAI 生效，提升为全局 |
| **v4** | **`endpointing`** | **120** | **500** | 120ms 时换气都会被判成「说完了」，长句碎成一片 |
| v5 | 「翻译预留」旋钮 | 有 | **删掉** | 改成固定规则（上屏前 0.7 秒开始翻译），不该让用户猜 |
| **v6** | **`capture.delayBitsPerSecond`** | **4000000** | **0（自动）** | 写死 4 Mbps 对 4K 太低，运动画面会糊 |

> **关于 v6：** 如果你在 v2.45 之前用过这个扩展，storage 里存着旧的 `4000000`，
> 它会**盖住新默认值** —— 结果就是**画质档位怎么调都没反应，码率恒为 4 Mbps**。
> v6 迁移会把它改成 0（自动）。手动填过具体码率的人不会被碰。
>
> **升级后如果"画面一动还是糊"，先去设置页确认一下「画质档位」和诊断面板里的
> `视频码率 · …` 那行是不是你预期的值。**

如果你之前**主动**关掉了「也翻译中间结果」，迁移会尊重你的选择、保持关闭——但弹窗会提示你，
并给一个「一键套用速度优先」的按钮。

### 体感参考

Deepgram + Google 免 Key、速度优先：**约 0.6–1.2 秒**开始出中文字幕，之后每秒左右刷新一次。
Deepgram 的中间结果本身约每秒推一条，这是服务端的节奏，不是扩展能优化的部分。

> **想进一步压缩"字幕晚于画面"**：需要让识别比画面跑得更快 —— 这就是**延迟画面**干的事
> （已实现，见第三节）。还有一条更激进的路是**前读音轨**（点播才好用，直播不可行），
> 取舍与未实现的部分见 [docs/delayed-playback.md](docs/delayed-playback.md)。

### 还有一个更激进的选择：Deepgram Flux

Deepgram 新的 `/v2/listen`（Flux）每 **0.25 秒**推一条 `Update`，比 Nova 的每秒一条细 4 倍，字幕跟手感会好一截。但它的限制很硬：**只支持 10 种语言，不含中文和韩文**，且不支持 `smart_format`。如果你的**源语言是英文**（抓英文视频/会议），值得一试；中文源则无缘。扩展目前没有实现 Flux，需要新增一个提供方。

## 八、已知限制

1. **一次只能捕获一个标签页。** 这是 `chrome.tabCapture` 的限制；切换标签页需要重新开始。
2. **无法捕获浏览器内部页面**（`chrome://`、扩展页、应用商店页）——Chrome 不允许。
3. **DRM 保护的音视频**（Netflix、部分音乐平台）可能捕获不到音频。
4. **原生 `<video>` 全屏时字幕叠加不了。** YouTube / B站 / Twitch 等用的是容器 `div` 全屏，没问题；只有网站直接把 `<video>` 元素全屏时无解（此时控制台会打印提示）。改用窗口模式或播放器自带网页全屏即可。
5. **标签页静音播放时没有音频流**，自然也没有字幕。
6. 播放受版权保护的付费内容时请遵守对应平台的服务条款。

## 九、常见问题

### 播放页显示「还没收到画面数据…」

**那不是扩展坏了，是它在等你给它画面。** 那行字里会带实时读数：

```
已等 15 秒 · 缓冲 0.0s · 收到 0 帧（掉 0） · 见底 0 次。
通常是来源画面静止、或那个标签页没有画面输出 —— 让它动起来试试。
```

- **`收到 0 帧`、`缓冲 0.0s` 一直不动** → 那个标签页确实没有画面输出。
  常见于**视频处于暂停**、或者页面本身是静止的（纯音频页、音乐播放页）。
  **让画面动起来（播放视频）它就会自动消失** —— 数据一到就收掉。
- **数字在涨但画面还是黑的** → 那是另一个问题，请把这份日志贴出来。

> ⚠️ 这个提示是**自动让位**的：一旦收到画面数据就立刻消失，不需要你点任何东西。
### 📋 报问题之前：先复制这份日志

**没有日志我没法查。** 好消息是它很容易拿。

**延迟画面的播放页**：面板在**左上角**，紧挨着它有一个 **「复制日志」** 按钮。
点一下，**完整日志就进了剪贴板** —— 比你手动拖选方便得多：面板上只显示**最后 60 行**，
而按钮复制的是**缓冲区里的全部（最多 400 行）**，关键那几行一闪而过的也在里面。

> 浏览器拒绝剪贴板时它会退回"选中文本"模式，那时在面板上拖选再按 Ctrl+C 就行。

**叠加模式**：同一个面板在**字幕上方**（内容一样）。弹窗里那个「复制」按钮**复制的是字幕历史（原文+译文），不是日志** —— 别拿那个来报问题。

**贴出来的时候，至少带上这五行**（基本能覆盖八成的问题分类）：

```
识别就绪 · 本地 VAD 自检通过 · 采用「640 窗」真人语音峰值 1.000（阈值 0.5）· Whisper @ http://127.0.0.1:8080/v1
视频码率 · 3840×2160@60 → 78.6 Mbps（高画质），已按 6.6s 延迟的内存上限收到 79 Mbps（原 128）
VAD · 帧 1211 · 概率 0.4151（峰值 1.0000，阈值 0.5）· 输入电平 0.0053 · 说话中 · 近 3s 有声 44%（其中峰值 1.00）
延迟测量 · 缓冲末尾落后实况 1.56s（已补进排期，所以字幕不再因此偏早）
缓冲 · 前方 5.7s · 见底 0 次 · 掉帧 4/788 ⚠ 缓冲够却在掉帧：编码/解码抢不到资源
```

**为什么非要这五行 —— 每行能判断什么：**

| 这一行 | 能判断出什么 |
|---|---|
| **`识别就绪`** | VAD 开箱自检过没过、**自检选中了哪个窗长**、Whisper 服务的地址对不对。这一行不对，后面全都不用看 |
| **`视频码率`** | 码率有没有**被内存上限夹住**（`已按 … 收到 …`）。画面糊或者卡，先看这里 |
| **`VAD`** | 最能分流的一行。**`近 3s 有声` 占比低**＝那段时间**真的没人说话**（正常，等就行）；如果**电平够高却一直不认**，日志会自己带上 **`⚠ 疑似 VAD 失效`** —— 这两种**修法完全相反**，不看这行没法区分 |
| **`延迟测量`** | 延迟**有没有越跑越大**。正常应该在目标附近小幅波动；一路涨说明播放头掉队了 |
| **`缓冲`** | 缓冲**见底几次**、**掉帧多少**。`⚠ 偏薄`＝缓冲快空了；`⚠ 缓冲够却在掉帧`＝瓶颈在编码/解码（CPU/GPU），不在网络 |

**再顺手说一句现象** —— 这四个方向要看的行不一样：

- **没字幕** → 看 `VAD`（是不是真没人说话）和 `识别就绪`
- **字幕不准** → 看音源情况，并试试上面「音源差、说话快」那节的两个档位
- **画面卡 / 糊** → 看 `视频码率` 和 `缓冲` 的掉帧数
- **延迟越跑越大** → 看 `延迟测量`，以及有没有 `延迟涨到 …s，已跳到目标 …`

> 更细的排查（两条通道怎么互相印证、每个数字的正常范围）见
> [七、太慢怎么办](#七太慢怎么办延迟排查)。

**Q：点了开始没反应 / 一直显示「连接识别服务…」**
A：看弹窗顶部的红色提示。最常见是 API Key 没填或填错；其次是网络到不了 `api.deepgram.com`。设置页的「测试识别连接」能直接给出原因。

**Q：字幕出来了但原声听不见了**
A：正常不会——扩展会把捕获到的音频重新接到扬声器。如果你勾了「静音原声」，取消即可。

**Q：字幕全是空白 / 只有原文没有译文**
A：说明翻译请求失败了，弹窗会显示「翻译失败：…」。免 Key 的 Google 通道在部分网络下不可用，换 OpenAI 或 DeepL。

**Q：识别出来的原文错得离谱**
A：① 检查「音频语言」是否设对（设成 `自动检测` 时 nova-3 走 `language=multi`，精度会略降，明确语言更准）；② 用「关键词表」补专有名词；③ 换更大的 Whisper 模型。

**Q：字幕偶尔整条消失 / 少了一句**
A：先看诊断面板有没有 `VAD · 丢弃一段识别结果 · …`。那是**质量闸门**在拦 Whisper 的幻觉
（音乐、掌声、静音片段上凭空吐出的片尾套话）。如果被丢掉的其实是真话，
把设置页的「最短话段」调小，或者把「静音确认」调大一点让它别切得那么碎。

**Q：用本地 VAD 时，字幕太碎 / 太长**
A：两个旋钮对着调：太碎就**调大「收句静音」**（900 → 1400）；太迟钝就**调小「静音确认」**。
注意这两项直接等于主要延迟，是一对取舍。

**Q：本地 VAD 启动时报「自检失败 · 所有调用方式都不响应」**
A：说明模型没被正确喂进去。诊断面板会把几种窗长各自的峰值概率列出来
（`其余变体：576 窗=1.000 · 512 窗=0.001 …`）——
**全是 0.00x 才是真失败**；只要有一个是 0.9x，说明自检会自己挑对，看下一行它就绪了没。

**Q：选了本地 VAD，但识别服务连不上 / 一直没结果**
A：① 确认本机那个 Whisper 服务真的在跑（**启动它的那个命令行窗口**还开着、没报错）；
② 地址**填到哪为止要看你的服务** —— 扩展会在它后面接 `/audio/transcriptions`，
所以服务挂在 `/v1/audio/transcriptions` 就填到 `/v1`，直接挂在 `/audio/transcriptions` 就不带 `/v1`；
**两种都试一下，报「未找到文件」通常是前缀多一段或少一段**；③ 看诊断面板的 `识别就绪 · …Whisper @ …` 那一行，
地址对不对一眼就知道。

**Q：用了 DeepSeek / Ollama，报 `model not found`**
A：设置页那家的「模型」输入框是空的。**扩展不会再拿别家的模型名兜底**（那只会让你更看不懂报错），
所以直接报出来了 —— 填上 `deepseek-chat` 或你在 Ollama 里 `pull` 过的那个模型名。

**Q：百度翻译报 54003**
A：触发 QPS 限流了。**百度免费版每秒只能请求一次**，而同传的中间结果每 400ms 就刷新一次。
把设置页的「也翻译中间结果」关掉，只在句子定稿时翻，能好很多。想彻底解决就换服务。

**Q：能在 Firefox 用吗**
A：不能。代码依赖 `chrome.tabCapture` + `chrome.offscreen`，Firefox 的 MV3 实现不提供 offscreen document。

**Q：怎么改字幕样式 / 加自己的识别服务**
A：字幕样式改 `content/content.js` 里的 `CSS` 常量；新增识别服务在 `lib/asr/` 下加一个模块并注册到 `lib/asr/index.js`，模块契约见 `lib/asr/deepgram.js` 顶部注释。

### 画面和声音一起没有，但字幕正常

这是**采不到可解码的帧**，不是扩展坏了。典型读数：诊断面板里 `缓冲 · 前方` 在涨，
但画面是黑的、也没有声音（声音来自延迟画面那个 `<video>` 的音轨，它不播就一起没有），
而字幕走独立的分析支路，所以照常出来。

两个原因，同一个机理：

- **采集帧率上限设得太低。** 录制分片是 250ms 一片，帧率太低时一片里连一个关键帧都没有，
  解码器解不出任何一帧。**低于 12 现在会自动按 12 走**，诊断面板里会说明。想不限制就填 `0`。
- **来源画面长时间静止。** Chrome 的标签页采集在合成器有新帧时才产帧，完全静止的页面
  可能长时间不产帧。让它动起来就好。

这两种情况现在都会显示一个遮罩说清楚（以前是一个零提示的黑屏）。


## 十、开发者笔记

- 全部为原生 ES Module，**没有构建步骤**，改完代码在扩展页点「重新加载」即可
- 改完代码建议先跑一遍自检（不需要 `npm install`）：

  ```bash
  node tools/manifest-check.mjs  # manifest / 路径 / DOM id / 硬约束
  node tools/smoke-test.mjs      # 模块加载 / 滤波器与 AGC / 断句状态机 / 预设 / 术语表 / 签名 / 防复发
  node tools/pipeline-test.mjs   # 音频引擎全链路，桩对象驱动
  node tools/worker-test.mjs     # service worker 状态机与消息路由
  ```
  四套一共 **649 项断言**（91 + 372 + 126 + 60）。
  `pipeline-test` 会桩掉 `AudioContext` / `AudioWorkletNode` / `WebSocket` / `fetch` / `performance.now`，
  真实走完「启动 → 分析支路 → PCM → 重采样 → ASR 事件 → 翻译（含上下文）→ 下发字幕 → 停止 → 重启」，
  覆盖字幕行复用、译文与原文错配、AGC 收敛与回落、识别滞后夹取、**翻译请求背压与定稿抢占**、缓存命中、去重、资源回收等不变量。
  `worker-test` 用带随机延迟的内存 storage 驱动 service worker，专门盯**并发下的状态单调性**。
  详见 `docs/` 与 `tools/README.md`。
- **历史版本有两套，都自动**（`node tools/bump-version.mjs patch` 一次搞定）：
  - **git**：逐行差异，能看"这行为什么变成这样"。机器上的 git 是便携版（MinGit），
    在扩展目录外的 `../_tools/git/`，**不在 PATH 里**——`tools/git.mjs` 会自己去找
  - **`_versions` 快照**：整份拷贝，零依赖，防的是"`.git` 本身坏了或误删"
  - `node tools/snapshot.mjs --list` 看快照，`--prune N` 清理，索引在 `../_versions/INDEX.md`
- service worker 用 `chrome.storage.session` 持久化运行状态，所以 SW 被回收后弹窗仍能读到正确状态
- 协议要点（都已按官方文档核对）：
  - Deepgram 浏览器端用 subprotocol 传 Token：`new WebSocket(url, ['token', apiKey])`；官方要求 10 秒内必须有数据或 `KeepAlive`，这里每 4 秒发一次；收尾用 `Finalize` 冲刷尾部音频，再 `CloseStream`
  - OpenAI Realtime 先 `POST /v1/realtime/client_secrets` 换 `ek_` 临时密钥（响应字段是**顶层 `value`**），再用
    `['realtime', 'openai-insecure-api-key.ek_...', 'openai-beta.realtime-v1']` 连 `wss://api.openai.com/v1/realtime?intent=transcription`。
    **不能**发 HTTP 头 `OpenAI-Beta`（该形态已下线，会 close 4000）；若服务端也拒绝 beta 子协议，代码会自动退化成不带该子协议重连
  - OpenAI 音频块用 `input_audio_buffer.append` + base64 PCM16；采样率走 24kHz（`format.rate: 16000` 未被官方明确背书，故不用）
  - 转写事件是 `conversation.item.input_audio_transcription.delta / .completed / .failed`（`.segment` 是独立的分段事件，不当作定稿处理，否则会重复出字幕）
- 消息协议（`LIVEDUB_*`）：
  - popup / options → SW：`START` `STOP` `TOGGLE` `GET_STATE` `GET_HISTORY` `CLEAR_HISTORY` `SET_MUTE` `APPLY_SETTINGS`
  - SW → offscreen：`OFFSCREEN_START` `OFFSCREEN_STOP` `SET_MUTE` `APPLY_SETTINGS`
  - offscreen → SW：`EMIT` `HISTORY_PUSH` `HISTORY_UPDATE` `LEVEL` `ASR_STATUS` `CAPTURE_ERROR` `TRANSLATE_ERROR` `STREAM_ENDED`
  - SW → content：`SUBTITLE` `STYLE` `RESET`；content → SW：`PING`
  - 字幕投递统一由 SW 转发（`EMIT` → `tabs.sendMessage`），offscreen 不直接碰 `chrome.tabs`
- 新增识别服务：在 `lib/asr/` 下加一个模块并注册到 `lib/asr/index.js`，模块契约见 `lib/asr/deepgram.js` 顶部注释；
  建议同时在 `tools/smoke-test.mjs` 里补一条构造断言
- 新增翻译服务：走 OpenAI 兼容协议的，只要往 `lib/translate/index.js` 顶部的 `OPENAI_COMPAT` 表加一行；
  其余的要自己写签名（`lib/crypto.js` 里有 MD5 / HMAC / SHA，都有标准测试向量）
- ⚠️ **端到端自检**：`tools/cdp-harness.mjs` 会用 Chrome DevTools Protocol 驱动一个真实浏览器实例
  加载扩展、播放测试音源、把播放页的诊断面板当**文本**读回来。
  它兜的是四套断言结构上抓不到的一类问题：**静态引用错误藏在测试从不执行的方法里** ——
  函数本身测得好好的，调用点却从来没被跑过。改完播放页 / 采集相关的代码，值得跑一次。
- 重新生成图标：`python tools/make_icons.py`（需要 Pillow）
